# Internationalization (i18n)

tamp ships in **English** and **Ukrainian**. All user-facing copy lives in
centralized per-locale JSON; a tiny runtime (`src/i18n/index.ts`) resolves
strings with `{name}` interpolation and correct plurals, and a Preferences
"Language" selector switches the UI live. This document explains how it works
and how to add a string or a language.

## Where strings live

```
src/i18n/
  index.ts       # the t() runtime — resolveLocale / setLocale / getLocale / t
  en.json        # English — the SOURCE OF TRUTH and the runtime fallback
  uk.json        # Ukrainian — mirrors en.json's key set
  i18n.test.ts   # unit tests for lookup, interpolation, fallback, plurals
```

- **`en.json` is the source of truth.** Every key that exists must exist here,
  with the canonical English copy as its value.
- **`uk.json` mirrors `en.json`.** It has the *same* set of keys, with natural
  Ukrainian translations. (Phase 2.5 of the rollout asserts key-parity between
  the two files.)
- The JSON is **statically imported and bundled** — there is no async loading
  and no network fetch (telemetry-free, works offline).

## Key naming convention

Keys are **nested by area**, addressed with a dotted path. Group by the UI
surface or concern the string belongs to:

```jsonc
{
  "videos":    { "empty": "No recordings yet" },     // → t("videos.empty")
  "converted": { "copyAll": "Copy all" },            // → t("converted.copyAll")
  "common":    { "save": "Save", "cancel": "Cancel" },
  "units":     { "parts": { "one": "{count} part", "other": "{count} parts" } }
}
```

Conventions:

- Top-level groups track an **area**: `videos`, `converted`, `prefs`,
  `common` (shared verbs/labels), `units` (count-based phrases), `errors`,
  `onboarding`, `update`, etc.
- Leaf keys are **camelCase** and describe the string's role, not its current
  English text (`copyAll`, not `copyAllFiles`; `empty`, not `noRecordingsYet`).
- Do **not** add keys for non-user-facing text: CSS class names, preset ids,
  log messages, and dev-only strings stay as plain literals.

## The `t()` API

```ts
import { t } from "../i18n";

t("videos.empty");                       // → "No recordings yet"
t("update.available", { version: "1.2" }); // → "tamp 1.2 is available"
t("units.parts", { count: 3 });          // → "3 parts" (en) / "3 частини" (uk)
```

`t(key, params?)` resolves the dotted `key` in the **active** dictionary and:

- **Interpolation** — replaces `{name}` placeholders with `params.name`
  (`String()`-coerced). Unmatched placeholders are left untouched; stray params
  are ignored.
- **Plurals** — if the value is a **plural object** (an object with at least an
  `other` key) and `params.count` is a number, the CLDR category is chosen via
  `Intl.PluralRules(locale).select(count)`, falling back to `other`. English
  uses `one`/`other`; Ukrainian uses `one`/`few`/`many`/`other`. (If `count`
  is missing or non-numeric, `t()` degrades to the `other` form rather than
  throwing.)
- **Fallback** — a key missing from the active locale falls back to the **`en`**
  dictionary; if it's missing there too (or points at a group instead of a
  leaf), `t()` returns the **raw key string**. `t()` **never throws**.

### Plural objects

A count-based phrase is stored as an object keyed by CLDR plural category, not
as a flat string. Every plural object **must** include `other` (the universal
fallback). Provide exactly the categories the language uses:

```jsonc
// en.json — English uses one / other
"parts": { "one": "{count} part", "other": "{count} parts" }

// uk.json — Ukrainian uses one / few / many / other
"parts": {
  "one":   "{count} частина",   // 1, 21, 31, …
  "few":   "{count} частини",   // 2–4, 22–24, …
  "many":  "{count} частин",    // 0, 5–20, 25–30, …
  "other": "{count} частини"    // fractions
}
```

Don't hand-roll `count === 1 ? "…" : "…"` logic in views — that's correct for
English but wrong for Ukrainian. Always go through a plural object so
`Intl.PluralRules` picks the category.

### Active-locale model

The runtime keeps a single **module-level active locale**: `setLocale(locale)`
swaps the active dictionary, rebuilds the `Intl.PluralRules` instance, and sets
`document.documentElement.lang`. `t()` reads that active state, so it takes no
locale argument. The locale is chosen once at startup (see below) and changed
only via the Preferences selector (which reloads the webview).

## How to add a string

1. **Add the key to `en.json`** under the right area, with the English copy as
   its value. Use a **plural object** if it's count-based.
2. **Add the same key to every other locale** (`uk.json`) with a correct,
   natural translation. Keep the key set identical across files.
3. **Reference it via `t("area.key", params?)`** at the call site — replace the
   hard-coded literal. Pass `{ count }` for plurals and any `{name}` params.
4. Run `bunx tsc --noEmit && bun run test`.

> Forgetting a locale won't crash anything — `t()` falls back to English — but
> it ships an untranslated string. The Phase 2.5 key-parity check is there to
> catch exactly that.

## How to add a language

Say you're adding French (`fr`):

1. **Create `src/i18n/fr.json`** mirroring `en.json`'s full key set, with
   French values. Use the **CLDR plural categories French needs** for every
   plural object — French uses `one`/`many`/`other`, so check each plural object
   has the categories that language requires (the universal `other` is always
   required; consult the Unicode CLDR plural rules for the rest).
2. **Register it in `src/i18n/index.ts`:**
   - add it to the `Locale` union: `export type Locale = "en" | "uk" | "fr";`
   - `import fr from "./fr.json";` and add it to `DICTS`.
   - extend `resolveLocale()` so `"fr"` passes through and `"system"` maps a
     `fr`-prefixed `navigator.language` to `"fr"`.
3. **Add it to the Preferences selector** — the "Language" radio group in
   `src/views/preferences.ts` (give it an autonym label, e.g. `"Français"`, so
   users recognize their language in any locale).
4. **Widen the setting validation** — add `"fr"` to the accepted set in the
   Rust `validate()` (and the `Settings.locale` type/union on the TS side) in
   `src-tauri/src/settings.rs`, so the new value round-trips and isn't rejected.
5. **Cover the font** — make sure the UI typeface includes the new script (see
   below).
6. Add tests for the new locale's plural categories and `resolveLocale`, then
   run `bunx tsc --noEmit && bun run test`.

## The UI font

The UI typeface is **Montserrat**, self-hosted via `@fontsource` and imported in
`src/fonts.css` (pulled into `main.ts`). Montserrat covers both **Latin** and
**Cyrillic**, so English and Ukrainian render in **one** consistent geometric
typeface — there's no per-script fallback mismatch. We import only the Latin +
Cyrillic subsets for the three weights the app uses (400/500/600); Fontsource
registers one `@font-face` per subset with the correct `unicode-range`, so the
browser fetches only what a given glyph needs.

The body `font-family` (in `src/styles.css`) names Montserrat first, then a
system fallback stack — `"Segoe UI", -apple-system, BlinkMacSystemFont,
system-ui, sans-serif` — and **every** fallback there also covers Cyrillic, so
the swap window before the webfont loads still renders Ukrainian correctly.

**Extending coverage to another script** (e.g. Greek, Vietnamese): import the
matching Fontsource subset(s) for each weight in `src/fonts.css` (e.g.
`@fontsource/montserrat/greek-400.css`). If a target script isn't a Montserrat
subset at all, add a script-appropriate webfont and chain it in the
`font-family` stack — but prefer a single family that covers the script to keep
one typeface across the UI.

## Backend native notifications

A handful of strings are shown by the **Rust backend** as native OS
notifications fired from the **global shortcut** — the stale-recording warning
and the "no recent videos found" message in `src-tauri/src/shortcuts.rs`. These
fire **without the panel open**, so the frontend `t()` runtime can't reach them.

They are localized **in Rust** instead: resolve the persisted `settings.locale`
(`system` → `en`/`uk` the same way the frontend's `resolveLocale` does) and pick
the message from a small in-Rust string map, behind the existing `notify` path.
This is the only place Rust holds translated copy; keep it minimal and in sync
with the corresponding intent in the JSON dictionaries.
